# 깡터 기획서 (MVP v0.1)

> 랜덤깡(블라인드 박스) 인형 양도·교환·구해요 게시판.
> 오픈톡방(2,000명+)의 세 가지 불편 — **글이 묻힘 / 검색 안 됨 / 누가 뭘 갖고 뭘 찾는지 정리 안 됨** — 을 해결한다.
> 서비스명 '깡터'는 임시 이름 (`APP_NAME` 환경변수로 변경).

## 1. 목표와 지표

| 단계 | 목표 | 측정 (자동 기록) |
|---|---|---|
| 출시 전 | 베타 신청 50명 | `beta_signups`, 유입경로 `?src=` |
| 출시 +2주 | 오픈톡방 사용자 100명 가입 | `signup` 이벤트 |
| 출시 +4주 | 첫 결제 1건 (끌어올리기) | `post_bumped(paid=true)` |

**North Star**: 주간 '연락하기' 클릭 수 (= 실제 거래 시도. 매칭이 거래로 이어지는지 보여 준다)

포트폴리오용 핵심 수치는 `/admin` 대시보드와 `python -m app.cli stats` 에서 바로 볼 수 있다:
가입자 · 게시글 · 거래완료 · 알림 신청 · 알림 매칭 · 알림 클릭률 · 연락하기 클릭 · WAU · 퍼널(가입→프로필→글/알림 작성→연락).

### 핵심 흐름
- **찾는 사람**: 검색 → 캐릭터 페이지 → 글이 없으면 🔔 알림 신청 → 올라오면 푸시/알림함 → 글 상세 → 연락하기(오픈채팅)
- **파는 사람**: 글쓰기(30초) → 같은 인형에 알림 건 사람들에게 즉시 알림 → 연락받음 → 거래완료 버튼
- **교환하는 사람**: 교환글 작성 → 반대 조건 교환글이 있으면 서로에게 '맞교환 상대' 알림

## 3. 데이터 구조

```
users ─┬─< posts ─┬─< post_items >── characters >── series
       │          └─< post_photos
       ├─< watches >── characters | series
       ├─< notifications >── posts
       ├─< push_subscriptions
       └─< reports >── posts
beta_signups      events (지표 로그)
```

| 테이블 | 주요 컬럼 | 비고 |
|---|---|---|
| `users` | provider(kakao), provider_id, nickname, openchat_url, kakao_talk_id, is_admin, is_banned | 연락처 둘 중 하나 필수 |
| `series` | name, brand, aliases, is_active, sort | 카탈로그 1단계 |
| `characters` | series_id, name, aliases, is_secret | 카탈로그 2단계. **모든 검색·알림·시세의 키** |
| `posts` | user_id, type(sell/trade/want), status(open/reserved/done/hidden), price, note, ship_method, view_count, bumped_at, done_at | 정렬은 `bumped_at` → 유료 끌어올리기는 이 값만 갱신 |
| `post_items` | post_id, character_id, role(have/want), price | 한 글에 여러 인형. 개별가 = 시세 데이터 원천 |
| `post_photos` | post_id, url, sort | 서버에서 1280px WebP로 변환, EXIF(위치) 제거 |
| `watches` | user_id, character_id 또는 series_id, post_types, max_price, is_active | "올라오면 알려주세요" |
| `notifications` | user_id, post_id, watch_id, kind(watch/mutual_trade), message, pushed, read_at | (user, post, kind) 중복 방지 |
| `push_subscriptions` | user_id, endpoint, p256dh, auth | 웹 푸시 |
| `reports` | post_id, user_id, reason, resolved | 사기 대응 |
| `beta_signups` | nickname, contact, interests, roles, source | 출시 전 수요 |
| `events` | name, user_id, post_id, props(JSON), created_at | 지표 단일 출처 |

**이벤트 목록**: signup, login, onboarded, post_created, post_viewed, contact_clicked, post_status_changed, post_done, post_bumped, watch_created, watch_matched, notification_clicked, push_subscribed, search, report_created, beta_signup, catalog_request

## 4. 기술 스택 / 배포 (월 0원 목표)

| 영역 | 선택 | 이유 |
|---|---|---|
| 서버 | **FastAPI + Jinja2 서버 렌더링** + 순수 JS | 이미 익숙한 스택. 프론트 빌드 없음 → 혼자 빠르게. 모바일 첫 화면이 가볍다 |
| DB | 로컬 SQLite / 운영 **Supabase Postgres (서울 리전, 무료)** | SQLAlchemy라 URL만 바꾸면 됨 |
| 이미지 | **Cloudflare R2** (10GB 무료, 전송료 0) | S3 호환 → 코드 수정 없이 교체 가능 |
| 호스팅 | **Google Cloud Run (서울, 최소 인스턴스 0)** | Docker 배포 경험 활용, 무료 사용량 안에서 운영 가능 |
| 로그인 | **카카오 로그인** | 사용자가 전부 카톡 사용자 |
| 알림 | **웹 푸시(PWA)** + 앱 내 알림함 | 무료. 아이폰은 '홈 화면에 추가' 후에만 → 알림함 배지가 기본 |
| 도메인 | .kr 또는 .com (연 1~2만 원) | 카카오 로그인 Redirect URI 등록용 |
| 결제(나중) | 토스페이먼츠 결제위젯 | 사업자등록 필요 (아래 6번) |

배포 순서는 README 참고. 콜드스타트(첫 요청 1~3초)가 거슬리면 Cloud Run 최소 인스턴스 1로 (소액 과금).

## 5. 4주 일정

| 주 | 할 일 |
|---|---|
| 1주 (지금) | 방장 허락 → **베타 페이지만 먼저 배포**(`PRELAUNCH=1`) → 오픈톡 공지. 카탈로그를 실제 인기 시리즈로 채우기(제일 중요) |
| 2주 | 카카오 로그인·R2·도메인 연결, 베타 테스터 10명과 비공개 테스트, 피드백 반영 |
| 3주 | `PRELAUNCH=0` 정식 오픈, 오픈톡 공지, 매일 지표 확인 |
| 4주 | 유료 끌어올리기 실험(결제 연동 or 수동 송금으로 가설 검증), 회고·포트폴리오 정리 |
| 이후 | AI 자동 태깅 (아래) |

## 6. 법·운영 체크리스트

- **통신판매업 신고**: 직전년도 통신판매 거래횟수가 50회 미만이거나 간이과세자이면 신고 면제 가능 (공정위 고시). 단, 면제돼도 전자상거래법상 표시·환불 의무는 남는다. 신고를 하려면 사업자등록이 먼저다.
- **사업자등록**: 매출이 생기면 필요하고, PG(토스페이먼츠 등) 계약에도 보통 필요하다. **인턴 중이므로 회사 취업규칙의 겸업 조항을 먼저 확인할 것.**
- **첫 결제 대안**: PG 계약 전에는 '끌어올리기 신청 → 계좌 송금 → 관리자가 수동 반영'으로 지불 의사만 검증하는 방법도 있다(매출 신고 의무는 동일).
- **통신판매중개**: 결제를 받지 않는 게시판이라 '거래 당사자 아님'을 약관에 명시(초안 포함). 안전거래(에스크로)는 제외 유지.
- **개인정보**: 개인정보처리방침 게시(초안 포함), 베타 신청자 정보 파기 기한 지키기.
- **사기 대응**: 신고 기능 + 연락 화면 주의 문구 포함. 반복 신고 사용자는 `is_banned`.
- 위 법률 내용은 일반 정보이며, 유료화 전에 세무사나 관할 구청에 한 번 확인하는 것을 권장.

## 7. AI 자동 태깅

### 7-1. 구현됨: 사진으로 자동 채우기 (`app/services/vision.py`)
- 비전 모델은 **읽은 그대로만** 출력(JSON): 이미지 종류, 시리즈 글자, 캐릭터별 이름표 글자·모자 동물·색·위치·HAVE/WISH 표시·시크릿 여부
- 카탈로그 매칭은 서버: 시리즈명/별칭 퍼지 매칭 → 캐릭터는 (이름표 글자 유사도, 동물 단어↔별칭) 점수 → 후보 3개, 0.6 이상이면 자동 선택
- GPT로 만든 이미지의 깨진 글자(洋迁愿→详迁愿)와 원에 가려진 이름표는 동물 단어로 보완
- 같은 이미지는 해시로 캐시(재호출 없음), 사용자당 하루 30회 제한
- 카탈로그에 없는 시리즈 → 관리자 일괄추가 형식 초안 자동 생성 → `/admin/vision` 에서 다듬어 추가 (카탈로그 성장 루프)
- 지표: `vision_parsed`, `vision_failed`, `vision_accepted(top1, top3)` → Top-1/Top-3 정확도

### 7-2. 다음 단계

1. 운영하면서 **글 사진 + 사용자가 고른 character_id**가 자동으로 라벨 데이터가 된다 (이미 저장 중).
2. 1차: CLIP/SigLIP 임베딩 + 캐릭터별 대표 벡터 최근접 검색 (학습 없이 시작).
3. 2차: 데이터가 쌓이면 파인튜닝. 글쓰기 화면에서 "이 인형 맞나요?" 추천 → 수락률을 지표로 기록.
4. 포트폴리오 스토리: "실사용 데이터로 라벨을 모으는 구조를 처음부터 설계" — KoELECTRA 파인튜닝 경험과 연결.
